# 仮説検証レポート - Issue #117

## 検証対象の仮説

### 仮説1: 複数コマンドの結果を結合した際のトークン量が成功率に直接影響する
- **判定**: Confirmed
- **根拠**: 現在 `search`・`impact`・`search --related` にはトークン量を制御する仕組みがない。件数制御（`--limit`）のみ存在し、1件あたりのコンテンツサイズは制御不可。`context` コマンドのみ `--max-tokens` で制御可能（#105で実装済み）。

### 仮説2: 5〜10KB程度が最適範囲
- **判定**: Partially Confirmed
- **根拠**: 具体的な数値の妥当性は性能検証データに依存するが、現在の推定式（1トークン≒4文字）で 5KB≒1,250トークン、10KB≒2,500トークン。この範囲を制御する機能が `context` 以外のコマンドに存在しないことは確認済み。

## コードベース照合結果

### 既存のトークン制御機能

| コマンド | トークン制御 | 件数制御 |
|---|---|---|
| `context` | `--max-tokens` あり（#105実装済み） | `--max-files` あり |
| `search` | なし | `--limit` あり |
| `impact` | なし | `--limit` あり |
| `search --related` | なし | `--limit` あり |

### トークン推定の実装
- `output/mod.rs`: `text.chars().count() / 4`（1トークン≒4文字の簡易推定）
- `output/llm.rs`: `<!-- estimated tokens: ~N -->` コメントを出力ヘッダーに付与（情報表示のみ、制限なし）

### `--max-total-tokens` 相当のオプション
- **存在しない**: 複数コマンド横断でのトークン量制御は未実装

## 結論
Issue #117 の提案は妥当であり、実装のギャップが確認された。主な実装対象:
1. `search`・`impact` への個別 `--max-tokens` オプション追加
2. 複数コマンド結果の合計トークン制御（`--max-total-tokens`）
3. 自動調整モード（関連度順ランク付けによる上限内最適化）
