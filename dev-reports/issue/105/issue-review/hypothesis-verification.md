# 仮説検証レポート: Issue #105

## 検証日: 2026-03-23

## 仮説一覧と検証結果

### 仮説①: `--max-tokens` はヘルプに記載があるが実効性が不明確
**判定: Partially Confirmed**

- `--max-tokens` オプションは実装済み（`src/cli/context.rs:214-224`）
- トークン推定は `text.len() / 4` で概算（`src/cli/context.rs:375-377`）
- **ただし**: snippet部分のみ計算対象。heading・symbol・パス情報は除外
- **ただし**: 上限超過時はエントリ全体をスキップするのみ（部分含有なし）
- E2Eテストも存在（`tests/e2e_context_pack.rs:272-297`）

### 仮説②: ファイルサイズが不均一な場合、少数のファイルでもトークン上限を超える
**判定: Confirmed**

- 現在の実装はgreedy方式で、上限超過時にエントリ全体をスキップ
- 大きなファイルが先頭にある場合、1ファイルだけで上限到達の可能性あり
- snippetは固定500文字制限（`src/cli/context.rs:287`）だが、ファイル内容全体ではない

### 仮説③: 上限を超えるファイルは先頭N行+末尾N行のみ含める等の戦略が必要
**判定: Confirmed（未実装）**

- 現在の実装にはsnippet動的短縮の仕組みなし
- 固定500文字制限のみ
- Issueが求める「先頭N行+末尾N行」戦略は未実装

## 現状の実装フロー

```
1. 関連ファイル検索・スコア順ソート
2. max_files で先頭N個を抽出（デフォルト20）
3. max_tokens で累積トークン上限を適用（greedy）
4. 各エントリをエンリッチ（見出し・スニペット・シンボル）
5. JSON形式で出力
```

## 改善が必要な点

1. **トークン計算の対象範囲**: snippet以外（パス、見出し、シンボル）もトークン計算に含めるべき
2. **動的snippet短縮**: トークン予算に応じたsnippet長の動的調整
3. **部分含有戦略**: 大きなファイルの先頭+末尾のみ含める仕組み
4. **トークン推定精度**: 日本語テキストでは `len/4` の精度が低い（UTF-8で日本語は3byte/文字）
